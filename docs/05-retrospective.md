# 实现复盘与后续工作

本节记录实现中实际观察到的问题。题号2，实际投入3.5小时；个人修改与验证明细不作统计。

最难的工程问题是把模型动作与可信状态分开：模型可以说完成，也可能调用过期报价、重复生成或忽略部分失败。解决办法是将计划、报价、交付物、费用和正式保存分开记录，工具负责约束，模型负责下一动作，最后从数据库核对完成。

实际调试经验：LangGraph即使运行同步CLI也会在线程池调用工具，SQLite连接的默认线程限制导致首次冒烟失败。执行层增加串行锁并允许该连接在受控线程间使用。另一次场景验证发现通用“校园”标签让环保主题误用毕业素材，检索改为优先最具体主题匹配；修复后通过相关场景。

费用与部分成功是同一问题：先成功视频4，图文失败后不能丢掉视频，也不能在补做图文时再次收4。逐项成功提交并绑定当前报价，使恢复后仍可独立复算总额8。

初版取舍：选择单Agent与本地合成工具，使动态路径可审查。用户随后要求增加YAML子智能体配置，当前已扩展为主Agent、内容创作和方案审查子智能体，共用受控工具、账目与调用额度；未做UI、真实发布或支付。业务状态恢复替代完整图检查点恢复，更容易核对已成功产物，但不承诺外部API的恰好一次执行。

此前单Agent版本的真实模型动态路径与重复评估已有记录；当前子智能体版本的验证详见03-evaluation.md。下一步是核对最终代码与证据、完成仓库提交，并填写GitHub地址和最终SHA。

真实模型阶段的新发现：一个数值正确的8单位方案仍可能被模型写成多渠道工作，说明只测总费用不足以证明业务范围真的精简。增加工具层单渠道约束与替代范围建议，而不是让错误方案直接保存；模型仍负责根据反馈选择新渠道与重新估算。根地址重复/chat/completions的404也促使接入层增加提前检查。修改前证据保留，修改后重新评估。

另一项实际失败是停止原因：模型从标准报价及替代项时间判断应停止，宿主却先看标准报价超预算而误报。修复依据预算可负担候选判定时间，不要求模型多估算一次来迎合固定序列。中间16/17、最终17/17及两批重复评估均留档；这比只保留最后成功日志更能说明修改依据。

子智能体验证暴露了两个新问题。第一，模型可能把writer角色当成content-writer名称，只有拒绝码而没有合法选项时难以修正；工具反馈现包含配置中的实际名称和角色。第二，提示词中的“生成一次后返回”没有阻止子模型在部分成功后反复使用旧报价。现用框架return_direct结束单次创作子图，把真实观察交给主Agent，由主模型继续重估算和委派。执行边界需要落实到框架行为，不能只依赖提示词；但重规划动作仍由模型依据观察选择。两次失败批次与修复后证据分别保留，详见03-evaluation.md。

实际用时：候选人自报3.5小时，超过建议投入的3小时；题面中的3小时是建议，不是硬性截止。自动运行的Trace另行保留时间戳，不用它替代人工工时。未完成部分及已知限制以03-evaluation.md和README为准。

再次复核发现原先79项测试未覆盖两个输出边界：当前报价虽然便宜却不满足必需双渠道时，预算缺口错误地被置为0；批量生成遇到首项失败后，后续尚未执行的项目也被标成failed。新增测试将“请求过”“实际执行失败”“依赖阻塞”分开检查，并用符合完整硬约束的候选计算缺口。本轮还新增C13/C14运行记录，避免只修代码而继续引用旧源码的证据。
