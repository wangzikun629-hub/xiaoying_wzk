# 实现复盘

题号 2，实际投入 4h。以下记录项目中遇到的问题和处理方式。

最难的是在模型调整计划后，仍然保证结果、依赖和费用一致。只按“视频已经生成”判断复用不够：渠道变了、引用素材更新了，或者改写依赖的基础文案换了，旧内容都可能不再适用。现在这些判断集中在 `planning.py`，估算、执行和最终输出使用同一套规则。历史结果保留，费用也继续累计；切回原渠道时可复用仍有效的内容组合。

部分成功也需要单独处理。视频成功、图文失败时，工具返回成功项和缺失项，主模型重新估算后只补图文。子模型曾在部分成功后反复使用旧报价，单靠提示词没能阻止。后来将创作子图设为一次生成调用后返回，由主模型根据工具结果决定下一步。

测试曾出现“看起来通过”的情况：断言放在模型调用内部，异常会被运行器捕获；无素材场景只检查没有产物，服务不可用也能满足条件。现在关键断言放在运行结束后，业务失败还要核对原因和实际工具观察。121 项测试中包含这类误报的回归检查。

保存成功后，SQLite 中的方案就是完成依据，图会停止继续请求模型。导出 Markdown 失败单独标记，不回滚已经保存的方案；未保存、工具失败和调用额度耗尽则明确返回未完成。

下一步先补内容质量评估：检查引用事实与正文是否一致，再评估脚本是否适合发布。接入真实运营工具后，还需要为外部请求增加幂等键和对账机制。目前的恢复保证只覆盖本地已提交结果，不能保证外部服务不会重复计费。
