内容任务规划 Agent 要求复核
==========================

复核对象是用户提供的题面与当前 `00-project-plan.md`。目前仓库只有规划材料，没有实现、测试结果和真实模型 Trace，因此本文结论仅针对需求与设计覆盖，不能解读为项目已通过验收。此次修订已同步写入规划文档。

实施更新：上述为开始实施前的复核背景。现有47项自动测试、最终17个Mock及17个真实子场景通过，三轮真实重复评估12/12通过，结果见 `03-evaluation.md`。旧失败保留；当前本地验证不代表已完成GitHub发布或候选人独立验证。

**1. 复核结论**

整体技术方向符合题意：Deep Agents 承担模型与工具的决策循环，业务工具及状态层负责约束执行和结果核验。最需要补齐的是“观察到部分成功后怎么继续”及“继续时怎么准确计费”，不能只做正常链路和遇错重试。

设计层面已补齐下列缺口；实现阶段每一条都需要实际代码和可核对证据。业务不变量包括费用不超预算、依赖满足、保留成功结果、失败尝试真实、保存状态可信；模型自然语言说明不是这些不变量的证据。

**2. 题面逐项映射**

| 题面要求 | 应交付的行为 | 验收证据 |
| --- | --- | --- |
| 预算与截止时间内完成活动方案 | 产出实际方案，执行前和保存时校验费用与预计完成时间 | C01、C04、C05、C09，方案与账目 |
| 输入主题、预算、截止时间 | 三字段即可运行；缺失字段明确返回；幂等 ID 可以自动产生 | C02a/b、C06，校验输出 |
| 合成素材、费用与耗时表 | 版本化 JSON 数据，可独立复算 | data 文件、确定性测试、运行元数据 |
| 素材检索、脚本生成、成本估算、方案保存 | 四工具均实际可调用，输入输出可追溯 | 工具代码、独立测试、Trace |
| 任务计划、步骤状态、工具结果、费用合计 | 版本化结构化计划，逻辑步骤及执行尝试，结果 ID 和费用明细 | 每个样例 output 与 trace |
| 已保存方案或未完成原因 | 保存成功有正式记录；未完成包括原因、缺口、成功与剩余步骤 | C01、C05、C09、C11 |
| 成本超限后调整 | 模型先看到不合格报价，再选择替代、重估或停止 | C04 的真实模型 Trace |
| 工具错误后调整 | 一次性故障与持续故障分开；模型收到错误后选择下一动作 | C03a/b 的真实模型 Trace |
| 部分成功后调整 | 结果粒度保留成功项，模型只补缺失项或合理降级、停止 | C07a/b 的真实模型 Trace |
| 保留已成功步骤 | 成功结果跨重规划与续跑存在，不重复计费 | 结果 ID、账目、C07b、C12 |
| 正常、缺信息、工具失败、预算超限、重复执行 | 每个必验点有可执行检查和实际记录 | C01～C06；缺字段分别测试 |
| 无可行方案时返回缺口 | 依据满足内容硬约束的候选集合计算，不虚构全局最优 | C05、C09，结构化不足原因 |
| 不能把失败步骤记成成功 | 失败尝试保留；恢复后新尝试可以成功 | C03、C07b、C11、C12 |
| 失败步骤续跑（官方加分） | 重启后复用已提交结果，重新检查剩余约束 | C12a/b，续跑前后对比 |
| 模型动作—工具执行—观察—再决策 | 框架循环是真实模型驱动，业务代码不替模型选 economy/backup | 至少两条真实动态路径 |
| 设置运行上限 | 工具与模型调用均受控，达到上限返回未完成并保留结果 | C08，调用计数 |
| 统一 GitHub 材料、至少三组证据 | 五份规定文档、依赖、配置例、测试与 examples | README 评审入口、最终 URL 与 SHA |

**3. 本次发现并修订的设计缺口**

| 优先级 | 原设计风险 | 已补充的约定 | 实现时检查 |
| --- | --- | --- | --- |
| 高 | `partial` 只有状态名，未定义成功项怎么入账、补做 | 按交付物提交成功结果；只计成功项；失败项单独耗时；剩余项重估 | 已付 4 + 待付 4 = 8，保留原成功 ID |
| 高 | 内容包只有 12/8 合计，难以核对预算和部分成功 | 视频 4、图文 4、可选多渠道改写 4 | 工具计算、账目、Trace 三者一致 |
| 高 | 有任务计划字段，但计划版本与依赖结构不够明确 | 稳定步骤与交付物 ID、依赖、计划版本、变更原因 | 无环；旧跳过项不能成为成功依赖 |
| 高 | 备用内容包与备用生成器混在一个 mode 中 | `tier` 与 `backend` 分开；换后端只补缺失交付物 | 交付范围不随工具替换而暗中减少 |
| 高 | 持续故障不能完整覆盖题面的一次失败注入 | 独立的一次性故障和持续故障，含触发条件与次数 | 故障由测试端控制，错误实际返回模型 |
| 高 | 精简可能删掉关键内容而仍宣告成功 | 自定义最低交付物；用户额外要求作为硬约束 | 不满足最低标准不得保存为完成 |
| 高 | 时间有估算但累计、重启与模型等待的规则不清 | 模拟时钟与墙钟模式分别定义，续跑不清零 | 保存前复查；停机不重置真实截止时间 |
| 中 | 超预算可能被误记为估算工具失败 | 区分工具成功、报价可行、任务完成 | 报价 12：工具 succeeded，budget_ok=false |
| 中 | 要求请求 ID 容易超出题面三字段输入 | 请求 ID 可自动生成；显式新 ID 用于新任务 | 相同三字段重复运行保持幂等 |
| 中 | 新报价与旧报价的有效边界不清 | 报价绑定计划、素材、后端、规则版本及状态 | 更换方案不能使用旧报价执行 |
| 中 | 单纯校验固定工具序列容易误判合理决策 | 不变量测试与特定演示路径分开 | 合理重试/换工具/停止均按实际观察评估 |
| 中 | 自加要求容易被误当成官方门槛 | 标注官方必需、项目承诺增强和实现选择 | 文档不把框架、SQLite、重复次数等说成题面强制 |

**4. 三条核心演示的判定**

预算演示：预算 10，首次标准报价 12，模型收到工具结果后选择精简，重新报价 8，随后生成、保存。检查标准报价没有入实际账目，最终实付 8。只出现一个费用 8 的最终方案不足以证明模型重规划。

一次失败演示：精简版报价通过，视频成功花费 4，图文失败花费 0，模型收到部分成功结果后补图文或选择备用；成功后总费用 8。检查视频结果 ID 不变、第一次图文尝试保持失败、后续图文成功有新的尝试记录。最终逻辑步骤可以恢复成功，不能改写失败历史。

不可行演示：预算 5，最低完整内容包 8；模型观察候选约束后停止，返回未完成、预算缺口 3、零生成费用和保存未执行。资料或内容硬约束没有可行候选时返回具体缺失条件，不能套用一个与当前要求不兼容的最低价格。

上述都是待实现验收标准，不是已产生的运行结果。工具耗时也须计入实际样例的累计时间。

**5. 官方要求与本项目增强的边界**

官方必需：主题/预算/截止时间、合成材料、四工具、六类交付信息、模型动态决策、成功结果保留、五类必验场景，以及统一规则中的运行上限、执行记录、可复制运行与仓库材料。

官方加分且本项目承诺：失败步骤续跑。

本项目增强：真实模型生成脚本、按交付物计费、SQLite 持久化、计划版本、重复真实评估、内容自评、多个故障类型与干净环境复验。它们服务于完成与证明题目要求，不能替代核心验收，也不冒充额外官方门槛。

当前最低内容包是为样例定义的业务范围，包含视频脚本与图文文案；题面没有强制所有方案都采用这两个形式。模型提供商、框架和运行方式是技术选择。12 次模型调用和 16 次工具调用是初始可配置上限，需按实际框架开销校准；无论如何调整，最终都必须有限且可验证。

**6. 后续评审入口**

完成实现后，以本表逐项填入真实代码位置、测试命令、examples 文件和结果，不仅填“已实现”。发现任何预算违规、依赖不满足却保存、失败记录被覆盖或成功结果丢失，均应先修复再更新验收状态。

规划覆盖本身不是验收证据；当前已生成离线与真实模型证据，评审以最终目录live-final及evaluation-final为准。
