内容任务规划 Agent 项目实施规划
================================

本文记录最初实施规划，规划中的数值示意本身不是运行证据。实际完成状态见下方实施更新及评估文档。计划基于用户考核规则与官方示例源码制定；参考了上游设计，没有直接运行或移植上游应用。

实施更新：47项自动测试通过，最终17个Mock和17个真实子场景通过，真实关键场景三轮评估12/12通过。实际接口与取舍以 `02-solution.md` 为准，实际验证以 `03-evaluation.md` 为准。初始12/16调用上限已调整为可配置的20/32，覆盖框架及脚本内部调用；模型按合法内容包选择形成计划，步骤依赖骨架由代码构造，不提供任意DAG编辑。用户要求暂不推送GitHub。

**1. 项目定位与完整交付**

项目暂名：Campaign Planner。面向内容运营人员，根据主题、预算和截止时间，产出一份可执行的内容活动方案，包含目标与受众、内容形式、发布渠道、脚本、执行步骤、依赖关系、费用与时间明细。任务完成以正式方案保存成功为准。

采用 Python 3.11+、Deep Agents、CLI、SQLite、本地 JSON 合成资料。使用一个负责决策的 Agent 和四个业务工具。完成全部必验场景，并将失败步骤续跑纳入本项目承诺交付；题面将其列为加分项，但本项目不再按时间不足而默认省略。界面、部署、真实发布和图片生成不属于当前交付目标，资源优先用于动态决策、可靠状态、内容质量和可复现验证。

按用户最新要求，不以三小时为开发上限，也不以预计投入时间代替完成标准。按可验收的里程碑推进，持续记录实际用时、失败实验与修复；只有实现、测试、真实模型证据和交付材料均满足约定，才能报告项目完成。

真实模型通过工具调用选择动作；业务工具可以使用本地函数或合成实现。模型与提供商通过配置选择，不预设候选人已经具备任何 API 账号。提供独立离线 Mock 入口，明确只验证流程。

**3. 输入、输出与业务边界**

CLI 输入采用 JSON，建议字段如下：

```json
{
  "request_id": "campaign-001",
  "theme": "毕业季校园影像征集",
  "budget": 10,
  "deadline": "2030-06-01T13:00:00+08:00",
  "preferred_tier": "standard",
  "allow_simplification": true
}
```

`theme`、`budget`、`deadline` 为业务必填；`request_id` 用于幂等。偏好是可选字段，预算与时间是硬约束。金额使用非负整数模拟单位，布尔值和非有限数值不作为合法金额。截止时间要求带时区。

调用方只提供题面三个必填字段也应可运行，不额外强制提供 `request_id`。未提供时由规范化主题、预算、截止时间和有效偏好生成稳定指纹作为默认请求标识，并向用户返回；显式创建新活动时使用新 ID。相同输入重复运行默认命中已有请求。模拟故障配置、live/mock、时钟覆盖等实验选项不混入业务需求，评估通过独立数据库与显式请求 ID 隔离，避免误复用其他实验结果。

默认分别使用 live 与 mock 状态目录，避免一次离线样例的幂等缓存被真实模式当作模型结果返回。显式指定共享数据库时校验证据模式，模式冲突则明确拒绝复用，不能只靠评估人员自觉换 ID。

本项目样例定义最低交付标准：活动目标与受众、至少一个发布渠道、视频脚本和图文文案、执行步骤与排期、费用和素材引用。这是选定的样例业务范围，不是题面强制的内容形式。标准版可增加多渠道改写。`allow_simplification` 只允许删除可选项；无论是否允许精简，都不能删除最低交付物。用户明确要求的渠道或内容类型作为额外硬约束。如果资料、预算或时间只能支持低于最低标准的内容，应返回未完成并保留草稿，不能以“精简版”名义宣布成功。

未提供预算或截止时间时，在调用模型和业务工具前返回 `needs_input` 与 `missing_fields`。格式错误、负预算、过期截止时间返回明确的校验结果，不补造输入。零预算是合法约束，可进一步得到没有可行方案的结论。

正常运行使用当前时间。评估允许传入明确标记的模拟时钟；例如 `--now 2030-06-01T10:00:00+08:00`。记录起始时间、时区、时钟模式和模拟耗时，避免示例在未来因日期过期而失效。模拟业务耗时不真实等待，也不代表真实项目工期已验证。

模拟评估模式的业务当前时间 = 固定起始时间 + 持久化的累计工具模拟耗时；真实时钟模式 = 当前墙钟时间 + 已累计模拟工作耗时。后者包含 API 等待及进程停机的墙钟流逝，同时明确模拟工作耗时未实际等待。报价、执行前检查、保存、续跑均使用同一套时钟规则。每次续跑不得清零已用时间；真实时钟模式下停机期间也会接近截止时间。估算使用规则表时间，实际模型请求超时等墙钟变化在下次检查时重新纳入。

最终结果必须包含：`request_id`、`run_id`、状态、任务计划、各步状态与依赖、工具结果摘要、计划费用、已发生模拟费用、时间明细、保存位置或未完成原因、Trace 路径。

任务计划是可核对的结构化对象，每步至少有稳定 `step_id`、交付物 ID、动作、依赖 ID、预计费用和耗时、实际状态、结果 ID；含 `plan_version` 和变更原因。首次估算登记模型提出的计划，重估算登记新版本；检索及估算前的动作也保存为执行步骤。新版本保留旧版本，已成功交付物引用原结果。业务运行步骤与方案内建议的运营执行排期分开输出，不把尚未实际发布的运营任务标成已执行成功。框架 TODO 只作展示，不是业务完成证据。

计划校验检查步骤 ID 唯一、依赖对象存在、无环、结果归属当前请求，以及工具动作与交付物一致。生成依赖合格素材和当前可行报价，多渠道改写依赖基础内容成功，保存依赖当前计划的全部必需交付物。变更计划不能通过引用旧版本的失效或跳过步骤绕过这些条件；被替换的旧步骤可保留为 `skipped`，但不能作为新计划的成功依赖。

正式保存还要求当前计划所有仍生效、承诺交付的内容项均成功，包括标准版已选择的多渠道改写。全局可选项一旦保留在当前计划里，就不能在生成失败后直接忽略；模型需显式调整计划、说明删除原因并重新估算，且不得违反用户硬约束和最低交付标准。

最终状态采用：`completed`、`needs_input`、`invalid_input`、`incomplete`。只有正式保存记录已提交，才能是 `completed`。未完成原因使用可测试的代码，例如 `no_materials`、`budget_infeasible`、`deadline_infeasible`、`tool_failure`、`execution_limit`、`model_unavailable`、`not_saved`。

**4. 费用和时间规则**

费用表放在 `data/cost_rules.json`，工具从中计算。模型只能选方案、渠道和工具参数，不能提交自己的费用合计作为事实。

| 工具或模式 | 成功费用 | 模拟耗时 | 说明 |
| --- | ---: | ---: | --- |
| `search_materials` | 0 | 1 分钟 | 本地检索，支持部分结果 |
| `estimate_plan` | 0 | 1 分钟 | 只估算，不扣款 |
| `generate_script`：standard | 12 | 120 分钟 | 较完整的多渠道内容包 |
| `generate_script`：economy | 8 | 60 分钟 | 精简的单渠道内容包 |
| `generate_script`：economy + backup 后端 | 8 | 60 分钟 | 备用本地生成方式，交付范围与精简版一致 |
| `save_plan` | 0 | 1 分钟 | 校验并正式保存 |

12 和 8 必须能分项复算，具体规则如下：

| 交付物 | 模拟费用 | 模拟耗时 | 是否必需 |
| --- | ---: | ---: | --- |
| 视频脚本 | 4 | 35 分钟 | 是 |
| 图文文案 | 4 | 25 分钟 | 是 |
| 多渠道改写 | 4 | 60 分钟 | 标准版可选项 |

standard = 视频脚本 + 图文文案 + 多渠道改写 = 12；economy = 视频脚本 + 图文文案 = 8。内容包模式与生成后端是两个独立维度：`tier=standard/economy`；`backend=primary/backup`。上表 `backup` 一行表示用备用后端完成精简版时的合计，不另创一个内容包等级。可见交付物 ID 以稳定逻辑项标识，不能通过随意换 ID 逃避已有结果复用。

上述为初始合成规则；实施时可调整，但数据、代码、测试、Trace 必须一致。脚本工具生成的内容包需要满足所选模式承诺的交付范围，不能只改价格。

模拟注入的单项生成失败消耗 1 分钟、该失败项费用为 0，明确故障发生在该项成功交付与计费之前；同一次调用中其他已成功项照常记录费用和耗时。其他失败类型也必须有统一规则。模型 API 的 token 消耗与业务模拟预算分开记录，不能混为同一金额。

估算输出必须包括：费用明细、当前已花费、剩余步骤费用、预计总费用、当前时间、剩余步骤耗时、预计完成时间，以及预算和时间是否满足。所有剩余步骤包括保存步骤。

预计总费用 = 已发生费用 + 当前方案尚未执行的费用。已经成功且被复用的步骤不重复计入剩余费用；被放弃但已经收费的结果仍保留在已发生费用中。估算本身不能收费，不能把 12 的拒绝报价与 8 的执行费用相加为 20。

生成前要求存在与当前内容包参数匹配的有效估算；参数改变必须重新估算。执行前重新核对剩余预算和时间，避免模型绕过估算或使用旧报价。正式保存前再次校验依赖与约束。

报价绑定 `request_id`、`plan_version`、素材 ID 及内容指纹、交付物集合、生成后端、规则版本和估算时的费用/时间状态。已用时间发生变化时重新检查可行性，报价不是无条件执行许可。部分完成后只估算尚缺交付物；更换后端也不得重复生成已有成功项。成功项的累计费用与计划剩余费用分别返回。

预算为 10 时，12 的报价应被标为不满足约束，而不是实际执行后再发现超支。模型观察报价后选择替代方案。对所有已登记模式均不可行的场景，工具可以提供最低费用与缺口；模型据此停止。若未检查完整候选集合，只能报告“当前已检查方案不可行”，不能声称所有方案都不可行。

不可行时返回可复算的结构化缺口：预算缺口 = max(0, 已发生费用 + 满足硬约束的最低剩余费用 - 预算)；时间缺口 = max(0, 最早可行完成时间 - 截止时间)。不存在满足内容或素材硬约束的候选方案时，说明是哪项条件未满足，不能用一个虚构的最低价格代替。所有停止结果仍带已成功结果、已花费费用和未完成步骤。

**5. 四个业务工具的契约**

| 工具 | 核心输入 | 返回内容 | 依赖与副作用 |
| --- | --- | --- | --- |
| `search_materials` | 查询词、素材类型 | 素材 ID、摘要、匹配与覆盖情况 | 无；结果存入状态 |
| `estimate_plan` | 结构化计划、内容包模式、渠道、生成后端、复用结果 ID | 计划版本、报价 ID、明细、约束检查、缺口 | 校验素材及参数；登记计划版本；不计费 |
| `generate_script` | 报价 ID、素材 ID、模式、后端、待生成交付物 ID | 脚本 ID、内容、成功与失败项、实际费用 | 必须有可行报价和足够素材；逐项提交成功与计费 |
| `save_plan` | 已成功结果 ID、当前计划版本 | 方案 ID、保存状态、校验摘要 | 读取可信状态组装正式方案；不信任模型传入的金额 |

统一返回结构：`status`（`succeeded/partial/failed`）、`result_id`、`data`、`error_code`、`retryable`、本次费用、本次耗时。`partial` 表示工具完成了部分工作，不能直接作为所有依赖已满足。

工具调用是否成功、报价是否可行、任务是否完成是三个不同概念：成功算出报价 12 时，估算工具为 `succeeded`，但 `budget_ok=false`；这不是估算器故障。拒绝执行无效报价不能产生成功交付物；生成失败也不能被后续备用成功覆盖成原尝试成功。

部分成功按交付物记录。例如 economy 先完成视频脚本，再在图文文案处失败：工具返回 `partial`，携带成功结果、视频费用 4、视频耗时 35 和失败耗时 1；数据库保留视频结果及其计费。模型看到结果后只补图文文案；重新估算为“已花费 4 + 待完成 4 = 预计总额 8”。备用成功后正式方案总费用为 8，不是 4，也不是 12。若没有任何交付物成功则为 `failed`，本次模拟费用为 0。每个成功项的结果与费用在同一事务提交。

检索返回部分素材时列出缺失类型，允许模型缩小内容范围或换查询；没有素材时禁止生成虚构素材来源。工具按素材 ID 验证资料是否存在。原始请求主题不得在重规划中被擅自替换。

脚本工具提供两种显式后端：真实运行使用模型根据检索素材、所选内容包和运营规则生成结构化脚本；离线运行使用本地模板。真实生成可以复用同一模型适配器进行普通模型调用，不要求额外构建子 Agent。备用方式可以是本地模板，但必须在工具返回和最终方案中标记降级来源、内容限制以及是否仍满足本次交付要求，不能静默冒充真实生成。

生成结果必须检查素材引用、主题、渠道、必需内容和结构；无法满足要求则返回失败或部分成功。生成内部发生的模型调用也计入整次运行的全局模型调用上限，并记录消耗与超时。业务模拟费用与真实 API 消耗继续分账。

**6. Deep Agents 决策循环与执行约束**

流程约定为：输入校验 → 幂等检查 → 加载规则与历史业务状态 → 模型选择工具 → 执行工具并更新记录 → 模型观察结果 → 继续、改方案或结束 → 宿主核对最终业务状态。

模型拥有选择素材查询、内容包模式、替代生成方式以及结束的权利。固定代码只负责输入检查、权限、依赖、算账、执行上限和成功验证。不得写死“报价超过预算就自动切 economy”作为重规划实现，也不得预制真实模型 Trace。

Skill 描述方案结构与决策原则，而不规定所有场景必须依次调用同一组工具。模型结束但没有保存记录时返回 `incomplete/not_saved`；模型说成功但工具失败时以工具状态为准。模型决定停止时保留原因，最终结构由宿主根据实际状态生成。

使用 Deep Agents 提供的工具循环及规则/Skills 接入方式；通过适配层或中间件记录事件和执行计数。官方提供自定义工具、中间件及检查点等扩展入口，具体接入以最终锁定版本为准。[定制文档](https://docs.langchain.com/oss/python/deepagents/customization)

初始限制：每次运行最多 12 次模型调用、16 次工具调用，单次模型调用配置超时。工具次数包含规划、文件等内置工具和非法调用尝试，不能只统计四个业务工具。达到任一限制立即返回 `incomplete/execution_limit`，保留成功结果。框架递归限制仅作额外防护，不把图步数误称为工具次数。

第一版业务工具串行执行；框架若一次产生多个工具请求，执行层仍按序检查约束并更新状态。内置委派工具应在选定版本中关闭或限制；不能假定传入空自定义子 Agent 列表就一定关闭默认委派。若保留委派，必须统一计数且不让它绕过业务工具。

Agent 可访问的文件后端仅用于规则、素材视图与草稿。SQLite 数据库、成本规则源文件、正式保存记录由宿主管理，不能靠内置文件写入改出一个“已成功”的结果。正式完成只接受 `save_plan` 提交的记录。

**7. 状态、幂等与失败续跑**

SQLite 是业务事实来源，最少保存三类记录：请求及输入指纹、步骤执行记录、最终方案。费用和时间变动与步骤结果一起提交；对外输出由这些记录派生。

步骤状态：`pending/running/succeeded/partial/failed/blocked/skipped`。一次失败的尝试一直保留为失败；重试产生新的尝试记录。依赖缺失是 `blocked`，旧方案被放弃是 `skipped`，均不能记作成功。检索成功后生成失败，检索结果仍可复用。

区分逻辑步骤状态与执行尝试结果：重试真正成功后，逻辑步骤可以变成 `succeeded`，但先前失败或部分成功的尝试不改写。最终输出同时包含逻辑步骤、尝试历史和当前使用的成功结果，避免把“失败后恢复成功”误解为禁止逻辑步骤恢复，也避免覆盖原失败证据。

相同 `request_id` 且规范化输入相同：已完成时直接返回同一方案 ID，不调用模型、不新增计费记录；未完成时返回已有状态，只有显式 `--resume` 才继续。相同 ID、不同输入返回冲突。不同 ID 即使输入相同也视作新业务请求。请求进行中再收到同一 ID，应返回进行中，避免启动第二个执行器。

为简化保存一致性，正式方案 JSON 与 `completed` 状态在 SQLite 同一事务内提交，并对请求设置唯一约束。Markdown 文件是该方案的导出视图，失败时单独报告导出失败与数据库中的有效保存位置；不能凭文件存在判定业务成功。数据库写入失败时不得返回保存成功。

`--resume` 纳入完整交付：读取同一请求的已成功结果与最新错误，开启新的有上限运行，交给模型决定剩余动作。需要重新评估剩余时间、预算与报价有效性。可从业务状态重新构建模型上下文，不宣称已经实现任意图节点或进程崩溃后的精确恢复；若接入检查点，应再验证它与业务事务的一致性。

续跑至少验证两类情况：生成失败后复用已检索素材；保存失败后复用已成功脚本而不再次生成、计费。续跑使用新 `run_id`，保持原 `request_id`；费用累计、旧失败尝试和所有成功结果均可追溯。进程重启后应能从 SQLite 恢复已提交状态，遇到结果未确认的执行记录时明确返回待确认状态，不能猜测执行成功或盲目重做。该恢复范围不包含真实外部支付或发布服务。

**8. 两条必须实际留证的动态路径**

路径 A：预算调整。起始偏好 standard，预算 10，允许精简，时间充足；模型调用估算得到 12，然后根据结果选择 economy，再估算得到 8，生成并保存。验收检查 12 只是报价，实际计费总额为 8。

模型可能直接选经济版，不能因此伪造 12 → 8 路径。为观察重规划，输入明确“先评估标准版，若不可行再考虑精简”，成本信息由工具提供；实际结果仍必须来自模型。若模型未走预期路径，如实记录，再设计另一条有业务意义的输入或工具反馈实验。

路径 B：工具失败。已成功检索、已获得可行报价后，economy 生成器首次返回 `generator_unavailable`；该故障在本次运行中持续有效，提示简单重复无益。模型选择 backup、重新估算，再生成和保存。成功的检索结果不删除，不重复收费。该路径应由真实模型选择备用方式，而不是异常处理器自动调用。

为直接覆盖题面“注入一次失败”，另设一次性故障：在指定请求的图文文案交付物第一次执行时失败，仅触发一次，后续同项可恢复；此前视频脚本成功。模型必须看到 `partial`、成功视频 ID 和费用 4，再选择仅补缺失项、改备用方式或有理由停止。故障配置由测试运行器注入，模型不能自己把故障开关关闭。一次性故障与持续不可用是独立用例，不能相互冒充。

路径 C：资料部分成功。素材检索返回有视频素材、无某可选渠道的素材。模型可换查询，或在允许精简且保留必需交付物的前提下删除可选渠道，再估算保存；如果缺的是必需素材且检索后仍无法满足，应返回未完成。记录实际变化的交付物、渠道、计划版本与原因。仅声明支持 `partial` 而没有一次模型观察部分结果后的实际动作，不构成这条路径的证据。

两条示意均不是现有实测结果。使用固定随机种子或温度也不能保证路径相同，因此将模型行为是否符合断言作为实际评估结果记录。

Trace 按调用 ID 记录序号、模型动作、工具参数、返回摘要、费用与时间变化、后续动作、可对外展示的简短决策依据。后续动作在下一次模型响应实际到来后关联，不提前生成。不要保存内部思维过程或 API 密钥。

运行元数据包含模型提供商/模型名、配置、依赖版本、时间模式、代码 SHA、数据规则版本、场景故障配置和证据模式（`live` 或 `mock`）。如果先生成证据再提交代码，在证据生成时记录对应代码状态，不能声称尚未存在的最终 SHA 已参与实验。

**10. 测试与评估方式**

确定性自动测试使用 Mock 模型或可控工具序列，验证预算与时间运算、工具依赖、有效报价绑定、保存事务、幂等与上限。测试禁止超预算生成、失败步骤被当成功、未估算生成、用旧报价执行变更后的参数、重复调用收费等关键错误。

真实模型评估覆盖正常、工具失败后的重规划、预算调整、无可行方案、检索及生成部分成功、素材不足和失败续跑。对最终状态、保存记录、金额、素材 ID 与动作序列执行程序断言，不能仅凭模型总结或截图判定通过。缺信息等在模型调用前结束的场景按真实宿主校验行为留证，不要求额外调用模型。

断言区分业务不变量与演示路径：所有可接受结果必须满足预算、时间、依赖、来源和状态一致性；一次性错误后模型可选择有依据的重试或备用方式，不强制每次同一工具序列。预算 12 → 8 的演示单独检查实际报价、模型改选和重新估算；只得到费用 8 的最终输出不能证明发生过重规划。持续故障用例检查模型是否选择替代方案或合理停止，不能把自动重试日志当作决策证据。

正常完成、工具失败重规划和预算调整三个关键场景，各计划使用同一固定配置独立运行至少 3 次，使用不同请求 ID 与隔离状态，报告每次结果和实际样本量。统计约束违规次数、完成率、合理调整动作、调用数、实际模拟费用与恢复结果。小样本只说明本次评估观察，不外推普遍成功率。调参后重新运行受影响用例，保留修改前后的失败与改进记录。

模型不可用时，离线入口独立运行，禁止静默切 Mock 后继续标为真实模型证据。真实评估失败、没有出现预期动作、达到上限都应保留实际文件，并写进 `03-evaluation.md`。

内容质量建立人工评估表：主题与目标受众匹配、素材引用可追溯、渠道与内容形式匹配、活动步骤可执行、脚本完整、预算降级后仍满足最低需求。每项 0～2 分，总分 12；建议样例达到 9 分且无虚构素材与缺失必需交付物。这个分数是本项目自定检查标准，不是官方评分，也不代替硬约束验收。

活动方案应写明目标、受众、核心信息、内容形式、发布渠道、相对排期、执行角色和建议观察指标；指标属于目标或建议，不捏造活动已经产生的转化结果。对代表性输出逐项保存评语；若未获得运营人员评价，应明确是开发者自评。模型自动评分可以作为辅助，不能替代工具状态核验或人工评价。
